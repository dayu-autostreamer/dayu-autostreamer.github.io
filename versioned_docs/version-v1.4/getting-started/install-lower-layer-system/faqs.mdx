# FAQs

:::tip[Debug Tips in Dayu System]

**If you encounter errors in dayu system, please follow these steps to troubleshoot and use FAQs to solve:**

✅ **Check Dayu Pods:** Use `kubectl get pods -n <your-dayu-namespace>` to check dayu pods status.
Use `kubectl logs <pod-name> -n <your-dayu-namespace>` and `kubectl describes pod <pod-name> -n <your-dayu-namespace>` to check log information in abnormal pods.

✅ **Check Dayu Core Resources:** Use `kubectl get svc -n <your-dayu-namespace>` and `kubectl get deployment -n <your-dayu-namespace>` to check services and deployments if pods are in unknown status.

✅ **Check Node Connections:** Use `kubectl get nodes` to check node status in the distributed cloud-edge system ('Ready' or 'Not Ready').

✅ **Check Sedna:** Check Sedna gm and lc logs with `kubectl get pods -n sedna -owide` and `kubectl logs <sedna-pod-name> -n sedna`.

✅ **Check EdgeMesh:** Check EdgeMesh agent logs with `kubectl get pods -n kubeedge -owide` and `kubectl logs <edgemesh-pod-name> -n kubeedge` if communication between nodes is blocked.

✅ **Check Cloudcore:** Use `systemctl status cloudcore` or `journalctl -u cloudcore -xe` on the cloud server to check cloudcore is running without errors.

✅ **Check Edgecore:** Use `systemctl status edgecore` or `journalctl -u edgecore -xe` on the edge device to check edgecore is running without errors.

✅ **Check Kubelet** Use `systemctl status kubelet` or `journalctl -u kubelet -xe` on the cloud server to check k8s administrator service is running without errors.

✅ **Check Docker:** If none of the `kubectl` commands or other k8s commands works, check docker container status with `docker ps -a` and check docker logs with `systemctl status docker` or `journalctl -u docker -xe`.

:::

## Question 1: kube-proxy report iptables problems

```bash
E0627 09:28:54.054930 1 proxier.go:1598] Failed to execute iptables-restore: exit status 1 (iptables-restore: line 86 failed ) I0627 09:28:54.054962 1 proxier.go:879] Sync failed; retrying in 30s
```

**Solution:** Clear iptables directly.

```bash
iptables -F && iptables -t nat -F && iptables -t mangle -F && iptables -X
```

The following message will occur when using `kubectl describe <podname>`  which is roughly related to network and sandbox issues.


## Question 3: metrics-server keeps unsuccessful state

**Reason:** Master node does not add taint.

**Solution:**
```bash
# add taint on master node
kubectl taint nodes --all node-role.kubernetes.io/master node-role.kubernetes.io/master
```

## Question 4: 10002 already in use

Error message 'xxx already in use' occurs when using `journalctl -u cloudcore.service -xe`.

**Reason:** The previous processes were not cleaned up.

**Solution:** Find the process occupying the port and directly kill it.
```bash
lsof -i:xxxx
kill xxxxx
```

## Question 5: edgecore file exists

When attempting to create a symbolic link in installing edgecore, the target path already exists and cannot be created.
```bash
execute keadm command failed:  failed to exec 'bash -c sudo ln /etc/kubeedge/edgecore.service /etc/systemd/system/edgecore.service && sudo systemctl daemon-reload && sudo systemctl enable edgecore && sudo systemctl start edgecore', err: ln: failed to create hard link '/etc/systemd/system/edgecore.service': File exists, err: exit status 1
```

**Reason:** `edgecore.service` already exists in the `/etc/systemd/system/` directory
if edgecore is installed more than once.

**Solution:** Just delete it.
```bash
sudo rm /etc/systemd/system/edgecore.service
```

## Question 7: EdgeMesh has successful edge-edge but failed cloud-edge connection

**Troubleshooting:**

First, based on the **location model**, ensure whether the edgemesh-agent container exists on the **visited node** and whether it is operating normally.

![Q7-2](/img/FAQs/Q7-2.png)

This situation is common since the master node usually has taints, which will evict other pods, thereby causing the deployment failure of edgemesh-agent.
This issue can be resolved by **removing the node taints**.

If both the visiting node and the visited node's edgemesh-agent have been started normally while this error is still reported,
it may be due to unsucessful discovering between the visiting node and the visited node. Please troubleshoot in this way:

1. edgemesh-agent at each node has a peer ID (generated with the hash of node name):
```
edge1:
I'm {12D3KooWFz1dKY8L3JC8wAY6sJ5MswvPEGKysPCfcaGxFmeH7wkz: [/ip4/127.0.0.1/tcp/20006 /ip4/192.168.1.2/tcp/20006]}

edge2: 
I'm {12D3KooWPpY4GqqNF3sLC397fMz5ZZfxmtMTNa1gLYFopWbHxZDt: [/ip4/127.0.0.1/tcp/20006 /ip4/192.168.1.4/tcp/20006]}
```

2. If visiting node and visited node are in the same LAN with internet IP, refer to Question 12 in [EdgeMesh Q&A](https://zhuanlan.zhihu.com/p/585749690). Logs of discovering node in the same LAN is  `[MDNS] Discovery found peer: <visited node peer ID: [visited IP list(include relay node IP)]>`.

3. If visiting node and visited node are across different LANs, check setting of relayNodes (Details at [KubeEdge EdgeMesh Architecture](https://link.zhihu.com/?target=https%3A//mp.weixin.qq.com/s/4whnkMM9oOaWRsI1ICsvSA)). Logs of discovering node across LANs is `[DHT] Discovery found peer: <visited node peer ID: [visited IP list(include relay node IP)]>`.

**Solution:**

Before deploy EdgeMesh with `kubectl apply -f build/agent/resources/`, modify file `04-configmap.yaml` and add relayNode.

## Question 8: GPU is not found on master

Use `nvidia-smi` to see GPU status on the cloud server. To support GPU in k8s pod on cloud server, extra plugin is needed.

> Please refer to the following link:
>[Installing the NVIDIA Container Toolkit — NVIDIA Container Toolkit 1.14.3 documentation](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html#configuration)

Configure as the link, and add `default-runtime` in '/etc/docker/daemon.json' (remember to restart docker after modification):
```json
{
    "default-runtime": "nvidia",
    "runtimes": {
        "nvidia": {
            "args": [],
            "path": "nvidia-container-runtime"
        }
    }
}
```

## Question 10: Sedna LC reports `lookup gm.sedna on 127.0.0.53:53: no such host` {#question-10-sedna-lc-dns}

During Dayu-Sedna installation, LC pods can be `Running` while their logs repeatedly report:

```text
client tries to connect global manager(address: gm.sedna:9000) failed, error: dial tcp: lookup gm.sedna on 127.0.0.53:53: no such host
```

With the Sedna release used by the current system, this also prevents edge RuntimeServices from completing activation. Their workloads may be running, but the resources remain `Activated=False`, `Ready=False`, and `AwaitingNodeAck` because LC cannot receive activation requests from GM.

**Reason:**

Dayu-Sedna v1.1 LC intentionally uses `hostNetwork: true` so that it can verify the node-local EdgeMesh route through `127.0.0.1:10551`. If `edged.clusterDNS` is empty or incorrect, the host-networked LC inherits the host resolver, such as `127.0.0.53`, instead of the EdgeMesh DNS server at `169.254.96.16`. The Kubernetes name `gm.sedna` therefore cannot be resolved.

> Keep `hostNetwork` on the current Dayu-Sedna LC. Removing it prevents the LC from acknowledging RuntimeService routes through the node-local EdgeMesh path.

**Troubleshooting and solution:**

1. Check which LC nodes cannot connect to GM:

   ```bash
   kubectl get pods -n sedna -o wide
   kubectl logs -n sedna <lc-pod-name>
   ```

2. On every affected edge node, check `/etc/kubeedge/config/edgecore.yaml`. The effective configuration must contain:

   ```yaml
   modules:
     edged:
       clusterDNS: 169.254.96.16
       clusterDomain: cluster.local
   ```

3. Confirm that the EdgeMesh agent on the same node is Ready and that EdgeDNS has started:

   ```bash
   kubectl get pods -n kubeedge -o wide
   kubectl logs -n kubeedge <edgemesh-agent-pod> | grep -E 'EdgeDNS|169.254.96.16'
   ```

   A healthy agent logs that EdgeDNS is running and listening on `169.254.96.16:53`.

4. After correcting `edgecore.yaml`, restart edgecore on one node at a time:

   ```bash
   sudo systemctl restart edgecore.service
   sudo systemctl status edgecore.service
   ```

5. Recreate the LC pod on that node because an existing pod keeps its old `/etc/resolv.conf`:

   ```bash
   kubectl delete pod -n sedna <lc-pod-name>
   ```

6. Verify the end state instead of relying only on Pod readiness:

   ```bash
   kubectl exec -n sedna <new-lc-pod-name> -- cat /etc/resolv.conf
   kubectl logs -n sedna <new-lc-pod-name>
   kubectl get runtimeservices.sedna.io -n <dayu-namespace>
   ```

   The LC resolver should use `169.254.96.16`, the LC log should show a successful GM websocket connection, and endpoint-bearing RuntimeServices should become `Activated=True` and `Ready=True`.

Do not permanently edit `/etc/resolv.conf`; it is generated for the pod and the change can be lost after a restart. Fix `edgecore.yaml` instead.

## Question 11: `169.254.96.16` cannot resolve a service or times out {#question-11-edgemesh-dns}

First distinguish this failure from [Question 10](#question-10-sedna-lc-dns):

- A query sent to `127.0.0.53` means the pod is using the wrong resolver; fix `edged.clusterDNS`.
- A query sent to `169.254.96.16` that times out means EdgeDNS is unavailable or unreachable on that node.
- A query answered by `169.254.96.16` with `NXDOMAIN` usually means EdgeMesh has not synchronized the Service and Endpoint data yet.

Check the following in order:

1. Verify `clusterDNS` as required in [EdgeMesh Installation](/docs/v1.4/getting-started/install-lower-layer-system/install-edgemesh#configure-edge-network-edge).
2. Verify that the node's `edgemesh-agent` is Ready and its logs show EdgeDNS startup without repeated errors.
3. On the affected edge node, verify the local edge API used by EdgeMesh:

   ```bash
   curl -fsS --max-time 3 http://127.0.0.1:10550/api/v1/services
   ```

   If port `10550` refuses the connection, follow [Question 32](#question-32-edgemesh-local-api).

4. Check the iptables chains as described in [Hybrid proxy | EdgeMesh](https://edgemesh.netlify.app/zh/advanced/hybird-proxy.html).
5. If the EdgeMesh image itself is unavailable on a newly joined node, follow [Question 24](#question-24-16925496-1653-io-timeout).

## Question 16: Deployment failed after forcibly deleting pod

Deployment creates pods. But after deleting deployment through `kubectl delete deploy <deploy-name>`, pods are stuck in 'terminating' status.

Then, use `kubectl delete pod edgeworker-deployment-7g5hs-58dffc5cd7-b77wz --force --grace-period=0` to delete pods. And the re-deployed pods are stuck in 'pending' state after assigning to node.

**Solution:**

Deleting pods with option `--force` does not actually terminate pods.

You should go to the specific node and manually delete the corresponding docker containers (including pause, see details at [Pause in K8S Pod](https://zhuanlan.zhihu.com/p/464712164))
```bash
# Check pod position on cloud
kubectl get pods -A -owide
# Delete docker containers on specific node (the position of pod)
docker ps -A
docker stop <container>
docker rm <container>
# Restart edgecore on specific node (the pod)
systemctl restart edgecore.service
```

## Question 18: Large-scale Evicted (disk pressure)

**Reason:**

The free disk space (usually root directory) is below the threshold (15%), and kubelet will kill pods to recycle resources (Details at [K8S Insufficient Resource](https://links.jianshu.com/go?to=https%3A%2F%2Fkubernetes.io%2Fdocs%2Ftasks%2Fadminister-cluster%2Fout-of-resource%2F)).

**Solution:**

The fundamental solution is to increase the available disk space.

If a temporary solution is needed, the threshold can be changed by modifying the k8s configuration.

Specifically, modify the configuration file and add `--eviction-hard=nodefs.available<5%`:
```bash
systemctl status kubelet

● kubelet.service - kubelet: The Kubernetes Node Agent
     Loaded: loaded (/lib/systemd/system/kubelet.service; enabled; vendor preset: enabled)
    Drop-In: /etc/systemd/system/kubelet.service.d
             └─10-kubeadm.conf
     Active: active (running) since Fri 2023-12-15 09:17:50 CST; 5min ago
       Docs: https://kubernetes.io/docs/home/
   Main PID: 1070209 (kubelet)
      Tasks: 59 (limit: 309024)
     Memory: 67.2M
     CGroup: /system.slice/kubelet.service
```

From the outputs you can see that configuration file is at directory `/etc/systemd/system/kubelet.service.d`
and configuration file is `10-kubeadm.conf`.

```bash
vim /etc/systemd/system/kubelet.service.d/10-kubeadm.conf

[Service]
Environment="KUBELET_KUBECONFIG_ARGS=--bootstrap-kubeconfig=/etc/kubernetes/bootstrap-kubelet.conf --kubeconfig=/etc/kubernetes/kubelet.conf"
Environment="KUBELET_CONFIG_ARGS=--config=/var/lib/kubelet/config.yaml --eviction-hard=nodefs.available<5%"

# add '--eviction-hard=nodefs.available<5%' at the end
```

Restart `kubelet`:
```bash
systemctl daemon-reload
systemctl  restart kubelet
```

You will find that it can be deployed normally (it's just a temporary method, the disk space needs to be cleaned up).

## Question 19: Executing 'iptables' report that system does not support '--dport'

When executing command `iptables -t nat -A OUTPUT -p tcp --dport 10351 -j DNAT --to $CLOUDCOREIPS:10003`, an error of not supporting `--dport` is reported.

**Reason:** The `iptables` version not support `--dport`:
```bash
# Check iptables version
iptables -V
# Version of 'iptables v1.8.7 (nf_tables)' does not support '--dport'
```

**Solution:**

## Question 28: Connection refused in dayu containers

In dayu system containers, connection refused error is reported when accessing services, but the pods are normal and logs show no error.

For Dayu RuntimeServices, check activation before treating this as stale iptables state:

```bash
kubectl get runtimeservices.sedna.io -n <dayu-namespace>
kubectl get pods -n sedna -o wide
kubectl logs -n sedna <lc-pod-name>
```

If the workloads are running but endpoint-bearing RuntimeServices remain `Activated=False` with reason `AwaitingNodeAck`, follow [Question 10](#question-10-sedna-lc-dns). Clearing the edgecore database does not repair a disconnected Sedna LC and can cause unnecessary data loss.

**Reason:**

Check the status of `edgemesh-agent` on edge nodes:
```bash
kubectl get pods -n kubeedge -owide
kubectl logs -n kubeedge edgemesh-agent-xxxxx # xxxxx is the pod name
```

Only when the edgemesh-agent logs explicitly show a service port conflict, check iptables on edge nodes:
```bash
sudo iptables -t nat -nvL
```

Redundant iptable rules are recorded in `KUBE-NODEPORT-CONTAINER`, `KUBE-NODEPORT-HOST`, `KUBE-PORTALS-CONTAINER` and `KUBE-PORTALS-HOST` (which are residual after stop system).

**Residual-state solution:**

If RuntimeService activation is healthy and the residual rules above are confirmed, temporarily flush the edgecore database on the affected edge node. This may cause data loss, so back it up first:
```bash
# Stop edgecore
sudo systemctl stop edgecore
# Backup kubeedge data
sudo tar -czf /tmp/kubeedge-backup-$(date +%F-%H%M%S).tgz /var/lib/kubeedge
# Flush kubeedge data
sudo rm -rf /var/lib/kubeedge
sudo mkdir -p /var/lib/kubeedge
sudo chown -R root:root /var/lib/kubeedge
# Start edgecore
sudo systemctl start edgecore
# Check edgecore status
sudo journalctl -u edgecore -f --no-pager
```

Another temporary solution is to reinstall kubeedge on edge node as [instruction](/docs/v1.4/getting-started/install-lower-layer-system/install-kubeedge#join-kubeedge-cluster-edge) shows.

The current [Dayu startup script](https://github.com/dayu-autostreamer/dayu/blob/main/dayu.sh) fixes this issue.

## Question 29: Edgecore fails to restart on JetPack 6 or cgroup v2

On JetPack 6 or other cgroup v2 systems, `edgecore.service` may repeatedly restart and report errors similar to:

## Question 31: Edge node cannot download from DockerHub or GitHub

Some edge nodes cannot directly reach DockerHub or GitHub, or keep timing out when `keadm join` downloads KubeEdge release packages and the `kubeedge/pause:3.1` image.

**Solution:**

Prepare the release packages and pause image before running `keadm join`.

1. Download the matching KubeEdge release packages on a machine that can reach GitHub, then copy them to the edge node:
```bash
scp keadm-v1.9.2-linux-arm64.tar.gz kubeedge-v1.9.2-linux-arm64.tar.gz <user>@<edge-node>:/home/<user>/
```

When joining, `--tarballpath` should be the directory containing `kubeedge-v1.9.2-linux-arm64.tar.gz`, not the tarball file itself:
```bash
keadm join --cloudcore-ipport=<cloud-ip>:10000 --token=<token> --kubeedge-version=1.9.2 --edgenode-name=<edge-node-name> --tarballpath=/home/<user>
```

Even with the release tarball prepared, `keadm join` may still access GitHub for `checksum_kubeedge-v1.9.2-linux-arm64.tar.gz.txt` and `edgecore.service`. If it hangs at `checksum_kubeedge...` or `[Run as service] start to download service file for edgecore`, make GitHub/raw.githubusercontent.com reachable or pre-provision these small files through a temporary local mirror/wget wrapper. Restore the system `wget` immediately after join if you use a wrapper.

2. If the cluster has an internal image registry, configure Docker on the edge node to use it. Merge the following key into `/etc/docker/daemon.json` instead of overwriting existing Docker settings:
```json
{
  "insecure-registries": ["repo:5000", "114.212.87.136:5000"]
}
```

Then restart Docker, pre-pull and tag the pause image:
```bash
sudo systemctl restart docker
docker pull repo:5000/kubeedge/pause:3.1
docker tag repo:5000/kubeedge/pause:3.1 kubeedge/pause:3.1
sudo systemctl restart edgecore.service
```

Finally, confirm that `kubeedge/pause:3.1` exists locally:
```bash
docker images | grep 'kubeedge/pause'
```

## Question 32: Edgemesh-agent is Running but logs 127.0.0.1:10550 connection refused {#question-32-edgemesh-local-api}

The `edgemesh-agent` pod may be `Running`, but its logs keep reporting:
```bash
Get "http://127.0.0.1:10550/api/v1/services...": dial tcp 127.0.0.1:10550: connect: connection refused
```

**Reason:**

The edge Kube-API endpoint is not enabled in edgecore. Edgemesh can start, but it cannot watch Services and Endpoints from `127.0.0.1:10550`.

**Solution:**

On the edge node, enable `edgeStream` and `metaServer` in `/etc/kubeedge/config/edgecore.yaml`:
```yaml
edgeStream:
  enable: true
  server: <cloud-ip>:10004

metaManager:
  metaServer:
    enable: true
    server: 127.0.0.1:10550
```

Then restart edgecore and check the local edge API:
```bash
sudo systemctl restart edgecore.service
curl -fsS --max-time 3 http://127.0.0.1:10550/api/v1/services
```

After a few seconds, `edgemesh-agent` logs should show cache sync or iptables update messages instead of repeated `10550 connection refused` errors.
